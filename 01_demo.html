Credit Risk Scoring: End-to-End ML with skiPatrol

Feature Store → tidymodels → Model Registry → SPCS Deployment

An end-to-end credit risk scoring workflow demonstrating how a fintech company can build, evaluate, and deploy credit-risk models entirely within Snowflake using R and the skiPatrol package (with skiLift for DBI/dbplyr connectivity).

Runs unmodified in three environments – local, Posit Native App, and Workspace Notebooks – via sfr_connect()/dbConnect(Snowflake())’s auto-detection. See RUNBOOK.md and _config.R. Validated locally end-to-end 7 Sep 2026 against a real account; supersedes 01_demo_samiul_original.qmd, which used ODBC and a hand-built Snowpark session as Native-App-specific workarounds – see RUNBOOK.md for why neither is needed with the P1-02 fixes.

What you’ll do:

  1. Explore lending data already in Snowflake
  2. Build reusable features in the Snowflake Feature Store
  3. Train competing models with tidymodels (logistic regression vs XGBoost)
  4. Evaluate and compare model performance
  5. Register both models in the Snowflake Model Registry with metrics
  6. Select the champion version programmatically and deploy via SPCS
  7. Score new applications via REST and SQL
  8. Verify autocapture (ML Observability)
  9. (Optional) Set up drift/performance Model Monitoring

Database layout (created by 00_setup.qmd):

Schema Contents
RAW_DATA Source tables — customers, payments, loans
FEATURES Feature Store (entity, feature views, dynamic tables)
TRAINING Materialised training datasets
MODELS Model Registry (versioned models, metrics, services)

Connect and Configure Database Context

No hand-built Snowpark session and no ODBC: sfr_connect() auto-detects the right strategy for whichever environment this runs in (local connections.toml, Native App OAuth profile, or a Workspace Notebook session – see _config.R and RUNBOOK.md). Database/schema/warehouse are still passed explicitly, regardless of environment: several registry/feature store calls (e.g. sfr_write_table()) issue unqualified SQL that relies on the session’s current database, which auto-detection alone doesn’t always set.

  schema = CR_REGISTRY_SCHEMA,

Define reusable features in the FEATURES schema using dplyr/dbplyr pipelines. Each Feature View is backed by a Snowflake Dynamic Table that refreshes automatically.

Features defined here are used identically in training and production scoring — define once, use everywhere.

Feature View 2: Payment Behaviour (Dynamic Table)

Aggregated payment history — captures delinquency patterns. Passes the dbplyr lazy table directly (contrast with the SQL string approach above).

Uses refresh_freq to create a Dynamic Table that Snowflake refreshes automatically — use this when source data changes frequently.

payment_query <- payments_tbl |>
  group_by(CUSTOMER_ID) |>
  summarise(
    AVG_DAYS_PAST_DUE  = mean(DAYS_PAST_DUE, na.rm = TRUE),
    MAX_DAYS_PAST_DUE  = max(DAYS_PAST_DUE, na.rm = TRUE),
    PCT_MISSED         = sum(ifelse(PAYMENT_STATUS == "MISSED", 1, 0),
                             na.rm = TRUE) / n(),
    PCT_ON_TIME        = sum(ifelse(PAYMENT_STATUS == "ON_TIME", 1, 0),
                             na.rm = TRUE) / n(),
    AVG_PAYMENT_AMOUNT = mean(PAYMENT_AMOUNT, na.rm = TRUE),
    TOTAL_PAYMENTS     = n(),
    .groups = "drop"
  )

fv_payments <- sfr_create_feature_view(
  fs,

  version      = "v1",
  entities     = customer_entity,

5. Model Training with tidymodels

Two models compared with cross-validation:

  • Logistic Regression — interpretable baseline, standard in credit risk
  • XGBoost — gradient-boosted trees, typically better predictive performance

Preprocessing Recipe

credit_recipe <- recipe(
  DEFAULTED ~ AGE + ANNUAL_INCOME + LOG_INCOME +
    EMPLOYMENT_LENGTH_YEARS + HOME_OWNERSHIP +
    AVG_DAYS_PAST_DUE + MAX_DAYS_PAST_DUE +
    PCT_MISSED + PCT_ON_TIME + AVG_PAYMENT_AMOUNT +
    TOTAL_PAYMENTS + TOTAL_APPLICATIONS + AVG_LOAN_AMOUNT +
    MAX_LOAN_AMOUNT + PRIOR_DEFAULTS + AVG_INTEREST_RATE,
  data = training_data
) |>
  step_dummy(HOME_OWNERSHIP) |>
  step_impute_median(all_numeric_predictors()) |>
  step_zv(all_predictors()) |>
  step_normalize(all_numeric_predictors())

Every inference request was logged to the model’s inference table (ML Observability). This feeds drift detection, performance tracking, and monitoring.

Note

Expected delay, not a bug — do not wait on this live. Autocapture writes to a Snowflake-managed inference table through an asynchronous pipeline, the same architecture SPCS uses for event-table logs/metrics — it is not synchronous with the inference response. Snowflake doesn’t publish a hard SLA, but the architecture (and event-table precedent) points to minutes-scale latency, roughly 1–10 minutes in practice. “Immediate visibility” in Snowflake’s own framing means you don’t have to build your own capture pipeline, not zero lag. Failed requests are never captured at all, only successful ones. This fully explains local testing seeing 0 rows after 60s (7 Sep) — that’s within the expected window, not a defect.

9. Optional: Model Monitoring

Note

Optional extra — skip this section for a shorter demo; it doesn’t affect anything before it. Sets up drift/performance monitoring on the deployed model via skiPatrol’s Model Monitoring API (R/monitoring.R), backed by Snowflake’s MODEL_MONITOR_* SQL functions. See skiPatrol/vignettes/model-monitoring.Rmd for the general API and Snowflake’s own Model Registry/Monitoring docs for the underlying concepts.

Validated live, 7 Sep – three real constraints not obvious from the vignette (found by testing against the real account, not documented anywhere beforehand):

  1. The model version must be logged with task = (added to Section 7 above) – monitoring a version registered without it fails outright (“Registry model must be logged with task in order to be monitored”).
  2. Classification models need prediction_class_columns/actual_class_columns, not prediction_score_columns/actual_score_columns (score columns are for regression). sfr_monitor_source() didn’t expose the class-column parameters at all before this session – added as part of validating this section (see RUNBOOK.md).
  3. Class columns must be numeric-encoded (0/1), not string labels – our deployed model returns "yes"/"no", which gets encoded below. The timestamp column must be TIMESTAMP_NTZ/DATE, not TIMESTAMP_LTZ (what CURRENT_TIMESTAMP() returns by default) – also handled below.

Stats and performance metrics compute immediately – confirmed live, no scheduled- refresh delay, unlike autocapture’s asynchronous pipeline in Section 8. Drift metrics are not included here – they require a baseline distribution to compare against (sfr_add_monitor()’s source config accepts a baseline table, not yet exposed via sfr_monitor_source()), which is unset by default and needs its own setup. Flagged as a follow-on, not blocking.

Key Advantages Over Traditional Workflow

Traditional (RStudio + Plumber) Snowflake (skiPatrol + SPCS)
Data exported to local machine Data stays in Snowflake
Manual feature engineering scripts Feature Store: define once, use everywhere
Model files on shared drives Model Registry: versioned, governed, with metrics
Plumber API on a VM SPCS: auto-scaled containers, no infra management
No inference logging Autocapture: every prediction logged automatically
Manual model comparison Registry metrics: programmatic champion selection
